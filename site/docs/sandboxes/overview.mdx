# Sandboxes

Polyaxon's sandbox plugin exposes process, filesystem, and PTY access inside the main container of a running service. It does not create a separate workload kind or isolation boundary: the image, container user, mounts, connections, and network policy remain those of the service run.

Use sandboxes when you need to inspect a live environment, run commands against the same image and connections as your workload, iterate on code in-cluster, or automate runtime actions from Python or the CLI.

Start with the [Sandbox Quick Start](/docs/sandboxes/quick-start/). It continues from the main quick start and establishes the `quick-start` project, `sandbox/sandbox.yaml`, `/workspace`, and `RUN_UUID` used throughout this section.

## Where Sandboxes Fit

Sandboxes are an end-user workflow. They sit between regular workload docs and operator setup:

- Use this section for launching, connecting to, coding in, debugging, and automating sandbox-enabled runs.
- Use [agent setup](/docs/setup/agents/overview/) to install and configure the agents that run workloads.
- Use [interactive service access](/docs/references/polyaxonfile/runtimes/services/interactive-access/) for the low-level service plugin behavior.
- Use the Python [sandbox client](/docs/references/sandbox/client/), [process](/docs/references/sandbox/process/), [filesystem](/docs/references/sandbox/fs/), and [PTY](/docs/references/sandbox/pty/) references when building applications or agents.
- Use the [sandbox CLI reference](/docs/references/cli/sandbox/) and [SSH CLI reference](/docs/references/cli/ssh/) for exact command options.

## Capabilities

Sandbox-enabled runs can support:

- Health checks with `sandbox.ping()` or `polyaxon sandbox ping`.
- One-off and streaming commands with `sandbox.process.exec()` or `sandbox.process.exec_stream()`, and their `polyaxon sandbox exec` equivalents.
- Background commands with `sandbox.process.exec_bg()`, or `polyaxon sandbox exec --detach` with output read through `polyaxon sandbox logs`.
- PTY sessions with `sandbox.pty`, or interactive shells with `polyaxon sandbox shell`.
- File access with `sandbox.fs`, or the sandbox upload, download, and directory listing commands.
- SSH access for local terminals, IDEs, SFTP, SCP, and tunnels.
- Reconnectable terminal sessions when `plugins.tmux` is enabled.

## Typical Workflow

1. Start a service run with the access plugins required by your workflow (sandbox, SSH, or tmux).
2. Wait until the run reaches a running state.
3. Connect from a Python process, the CLI, SSH, or a notebook service.
4. Inspect files, run commands, install temporary packages, or debug runtime state.
5. Persist useful outputs to the run's outputs path or commit code changes back to a Git remote.
6. Stop the service run when the session is done.

## Minimal Polyaxonfile

```yaml
kind: component
version: 1.1
name: sandbox-dev

plugins:
  sandbox: true

run:
  kind: service
  container:
    image: python:3.11
    command: ["sh", "-lc", "mkdir -p /workspace && exec sleep infinity"]
```

This creates a regular long-running service with sandbox process and file access. Add `plugins.ssh: true` for native SSH access or `plugins.tmux: true` for reconnectable `polyaxon ops shell` sessions. These plugins add capabilities to the service; they do not create a separate sandbox workload.
